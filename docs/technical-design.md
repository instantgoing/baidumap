# 技术设计

文档版本：`competition-finalization-v1`
应用版本：`0.6.0-stage6`
内部坐标系：BD-09

## 1. 设计目标与边界

邻里半径把“15 分钟生活圈”分成三类确定性结果：真实步行路网等时圈、民生设施 POI 覆盖、1 公里设施服务盲区。大模型不参与达标判定，评分与报告均由版本化规则生成。

本轮在既有 P1–P4 与 P7 基础上补齐比赛收口证据：独立真值模板/计算器、逐点与批量 RouteMatrix 多轮基准、七类故障注入和页面错误/降级状态。P5 规划优先级、新设施选址、改善量估算与规划前后对比仍未实现，也不作为核心评分证据。

## 2. 系统结构

```text
React + Vite
  ├─ 选点：地址 / BD-09 坐标 / 地图点击
  ├─ IsochroneEngine：采样、收敛、插值、几何修复、边界复核
  ├─ 地图层：等时圈 / 耗时 / POI / 灰区 / 候选质心
  └─ ReportModel：确定性评分、证据与 HTML/PDF 导出
         │ REST + GeoJSON
FastAPI
  ├─ 统一请求/响应契约与错误映射
  ├─ BaiduMapClient：超时、重试、QPS、并发、缓存、熔断
  ├─ PoiPipeline：分页、标准化、归类、去重、空间筛选
  └─ BlindSpotEngine：1 公里网格、服务缺失与聚合灰区
         │ HTTPS
Baidu Maps Web Service API
```

前端在 `mock` 模式使用仓库内固定快照，不请求后端或百度服务。`online` 模式才通过 `/api` 访问 FastAPI。

## 3. API 策略

### 3.1 契约

- 成功：`{ "ok": true, "data": {}, "meta": {} }`。
- 失败：`{ "ok": false, "message": "...", "error": { "kind": "..." }, "meta": {} }`。
- 前端每次请求生成 `X-Request-ID`，后端原样回传，用于日志关联。
- `meta` 记录来源、耗时、API 版本和不含密钥的配额指标。
- 内部经纬度字段始终为 `{ lng, lat }`；调用百度接口时由适配层处理上游参数顺序。

### 3.2 上游调用

| 能力 | 上游用途 | 本地处理 |
| --- | --- | --- |
| Geocoding / Reverse Geocoding | 地址与 BD-09 坐标互转 | 统一字段和状态码 |
| Coordinate Convert | WGS84/GCJ-02 转 BD-09 | 验证点数和输出顺序 |
| Place Search | 2 公里多关键词检索 | 分页、归类、去重与二次空间筛选 |
| Walking RouteMatrix | 一起点到最多 50 终点 | 分批、状态归一化与样本证据 |
| DirectionLite walking | 获取单路线分段几何 | 沿路线截取目标耗时点 |

`GET /api/health` 只检查配置；`GET /api/health?verify=true` 才会越过缓存执行一次真实地理编码探测。

## 4. 等时圈算法

1. 从中心点向 36 个方位生成 5 档极坐标候选点。
2. 使用 Walking RouteMatrix 分批获取真实路网耗时和距离。
3. 对目标耗时两侧执行边界收敛，时间容差默认 ±60 秒，空间区间默认 50 米。
4. 相邻方向半径比超过 1.3 时增加中间方向，总方向不超过 72。
5. 对少量失败方向做相邻插值，对局部尖峰做离群修复；必要时用凸包保证 GeoJSON Polygon 有效。
6. 抽取最多 12 个主方向、均匀方向和局部凹陷点，以 DirectionLite 单路线几何截点，再用 RouteMatrix 做同源内部交叉复核；独立人工真值另由核验数据集提供。
7. 输出 Polygon、采样热力、批次/迭代指标、复核通过率、置信度和限制。

置信度不只取决于返回点数，还结合样本成功率、插值占比、修复数量和内部交叉复核。低置信结果会携带警告，不会被标成精确边界；同一百度路线体系的复核不冒充独立人工准确率。

## 5. POI 清洗管线

1. 以 10 个民生关键词在中心周边 2 公里检索，最多 8 页、每页 20 条。
2. 保留 `uid`、名称、地址、位置、上游类别、来源关键词和采集时间。
3. 依据版本化词典归一到八类民生设施，排除成人教育、培训机构和保健品店等明显误召回。
4. 优先按百度 `uid` 去重；无 `uid` 时按标准化名称和 50 米空间阈值去重。
5. 先按 2 公里检索区二次筛选，再按等时圈 Polygon 筛选报告 POI；没有有效 Polygon 时明确降级为 1 公里半径。

多源数据不直接混入运行时：百度 Place Search 是候选主源；政府公开名录、机构官方页面/电话和实地记录只做独立核验；固定快照只做离线演示。跨来源使用名称/地址归一、UID、空间距离与名称相似度形成可审计 cluster，所有类别、地址、营业状态冲突均保留原值并进入人工复核。完整字段、阈值、许可与测试案例见 `docs/multi-source-poi-strategy.md`。

## 6. 盲区算法

- 在中心周边 1 公里生成方形网格，间距可配，当前页面为 200 米，真实报告采用 150 米。
- 对每个网格分别判定菜市场、药店和小学 1 公里内是否存在。
- 初筛使用球面距离；接近阈值的候选网格最多抽取 20 个，用 Walking RouteMatrix 路网距离复核。
- 任一必测类别缺失即为盲点；相邻盲点按网格邻接聚合为灰区。
- 灰区输出缺失类别、网格数、面积、人口代理、范围设施计数和边界候选数。人口代理只是“面积 × 配置密度”，不是人口普查数据。

## 7. 缓存、并发与失败语义

- TTL 缓存键包含端点名和归一化参数，命中缓存不消耗上游配额。
- 并发信号量限制同时上游请求；独立滑动窗口限速器限制 QPS。
- 只对可重试失败执行带随机抖动的指数退避。连续失败达阈值后熔断，冷却期内直接返回可识别错误。
- 上游空结果、无路线、429、5xx、超时、无效 AK 保留不同错误语义。页面不会把失败显示为成功。
- 离线样例是用户显式选择的可复现模式，不是在线失败后偷换的“真实结果”。
- 前端单请求默认超时为 180 秒，用来覆盖低 QPS 下最多 20 个盲区边界复核；后端每次上游请求仍保留更短的 12 秒超时。

在线等时圈失败但 POI 分析可继续时，页面会明确标记 `degraded` 并说明改用 1 公里半径；POI 分析失败则保持 `error`。系统不会在在线失败时自动切换固定快照。逐点/批量、冷启动/缓存和在线/模拟证据分层见 `docs/engineering-evidence.md`。

## 8. 安全边界

- 服务端 AK 只从 FastAPI 运行环境或本地 `backend/.env` 读取，不进入前端包、响应、日志或样例。
- 浏览器端 AK 仅用于 JSAPI GL，必须配置 Referer 白名单；不得将它当作 Web Service AK。
- 后端 CORS 默认只允许本地开发源，生产环境必须显式列出域名。
- 仓库忽略 `.env`、`.env.local`、`.env.*.local` 和日志；CI 对完整 Git 历史执行 Gitleaks。
- 不抓取百度地图网页，不绕过配额，不将第三方地图数据以 Apache-2.0 重新授权。

## 9. 可复现性与运维

- 前端依赖由 `package-lock.json` 锁定，CI 使用 `npm ci`。
- 后端使用兼容版本范围，镜像构建时保留安装日志；正式发布应再生成锁定文件和 SBOM。
- `npm run demo` 强制离线快照，`docker compose up --build` 默认为在线三服务部署。
- 报告显示数据时间、来源、算法版本、样本数、置信度、边界复核和限制。
