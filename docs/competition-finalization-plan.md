# 参赛收口五项要求与开发提示词

文档版本：`v1.0`
编制日期：2026-09-14
适用项目：邻里半径 · 15 分钟生活圈
赛道：开源 AI 工具赛道

## 1. 目标与执行原则

本轮工作的目标不是继续无边界扩充功能，而是依据比赛 PDF 的四项评分维度，将现有项目整理成可运行、可验证、可复现、可答辩的正式参赛作品。

比赛评分重点为：

- 功能正确性与覆盖率：40%。
- API 深度调用与工程优化：30%。
- 产品交互与用户体验：15%。
- 开源工程规范：15%。

执行时遵守以下原则：

1. 优先补齐评分证据，再开发非硬性加分功能。
2. 真实在线数据、人工核验数据与固定演示快照必须清晰区分。
3. 不编造 POI、准确率、性能数据或实地核验结论。
4. 不绕过百度地图配额、QPS 限制或数据使用规则。
5. 服务端 AK 不得进入前端包、日志、文档、样例数据或 Git 历史。
6. 所有结论必须能回溯到数据时间、来源、参数、算法版本和验证方法。
7. P5 规划前后对比不是评分表中的硬性要求，仅在以下五项完成后作为加分项考虑。

## 2. 要求一：建立独立比赛仓库与发布基线

### 目标

将当前 `baidumap` 目录作为独立仓库根目录发布，确保评委可以直接找到源码、README、许可证、Docker 配置和 CI 工作流。

### 开发任务

- 制定独立仓库发布步骤，不在当前多项目父仓库中直接进行破坏性 Git 操作。
- 确认新仓库根目录包含 `.github/workflows/ci.yml`、`README.md`、`LICENSE`、`NOTICE`、前后端源码、测试和文档。
- 检查 `.gitignore`，确保 `.env`、`.env.local`、`.env.*.local`、日志、构建物和测试产物不会提交。
- 在独立仓库中执行完整 CI，并确认前端、后端、容器构建和密钥扫描任务全部通过。
- 固化正式比赛版本，例如 `v1.0.0-competition`，记录提交哈希、发布日期和演示数据哈希。
- 补充比赛平台、截止时间、仓库 URL、线上演示 URL 和团队信息；未知信息保留明确的 `待填写`，不得猜测。

### 验收标准

- 评委从仓库首页能够找到一键运行、在线模式、离线演示和测试方法。
- Git 平台实际识别并执行 `.github/workflows/ci.yml`。
- CI 所有任务为绿色，仓库历史中不存在真实 AK。
- 在一台干净环境中，仅根据 README 可以启动固定演示。
- 发布版本能够通过标签或 Release 被准确复现。

### 证据产物

- 独立仓库 URL 与 Release URL。
- CI 成功截图或状态徽章。
- 发布版本、提交哈希和演示数据 SHA-256。
- 干净环境启动记录。

## 3. 要求二：补齐真实社区独立验证

### 目标

证明等时圈、POI 分类和服务盲区不仅能够运行，而且具备可量化的正确性证据，重点支撑 40% 的“功能正确性与覆盖率”。

### 开发任务

- 选择一个主要样例社区，并选择一个存在河流、封闭道路、立交、施工或明显绕行的对照中心点。
- 独立核验不少于 30 条民生设施，菜市场、药店、小学各不少于 5 条。
- 每条记录至少包含：记录编号、名称、类别、地址、坐标、是否营业、百度 POI UID、核验来源、来源 URL 或实地说明、核验日期、核验人和备注。
- 核验来源优先使用政府公开名录、设施官网或官方电话、学校/医疗机构公开页面和实地记录；不得将同一条百度 POI 返回结果当作独立真值。
- 保留至少 12 个方向的边界复核，记录系统预测耗时、人工步行规划耗时、绝对误差、入口偏移和道路阻隔说明。
- 从灰区内部、边缘和非灰区分层抽样，记录三类必测设施是否真实缺失。
- 根据明确公式计算 POI 查全率、分类准确率、边界耗时误差、灰区准确率和灰区召回率。
- 更新真实社区报告，展示样本量、数据时间、误差案例、结果与限制。

### 指标口径

- POI 查全率 = 系统正确检出的真实 POI 数 / 独立真值中的真实 POI 总数。
- 分类准确率 = 分类正确的系统 POI 数 / 已完成人工核验的系统 POI 数。
- 边界绝对误差 = 系统预测步行秒数与人工复核步行秒数之差的绝对值。
- 灰区准确率 = 实际为灰区的预测灰区样本数 / 全部预测灰区样本数。
- 灰区召回率 = 被系统识别出的真实灰区样本数 / 全部真实灰区样本数。

如独立真值覆盖不足，必须将指标标记为“样本内结果”，不得外推为城市总体准确率。

### 验收标准

- 独立核验记录不少于 30 条，三类必测设施均达到最低样本量。
- 至少包含一个成功案例和一个明确误差案例。
- 所有指标均可从原始核验记录重新计算。
- 报告同时展示结果与局限，不隐藏错误样本。
- 样例快照不得冒充本次真实验证数据。

### 证据产物

- 独立核验数据表。
- 指标计算脚本及自动化测试。
- 更新后的 `docs/real-community-report.md`。
- 主要社区与道路阻隔对照社区的截图和案例说明。

## 4. 要求三：形成 API 深度调用与工程优化证据

### 目标

将项目中已经存在的批量 RouteMatrix、扇形采样、空间插值、缓存、重试、限流和熔断能力转化为评委能快速理解和复现的量化证据。

### 开发任务

- 建立可重复的性能基线，记录机器环境、运行模式、中心点、参数、运行次数和统计口径。
- 对比逐点请求与批量 RouteMatrix 的上游调用次数、总耗时、成功率和配额消耗。
- 对比冷启动、缓存命中以及不同采样方向数量下的耗时和边界误差。
- 增加可离线运行的故障注入或录制快照测试，至少覆盖：无 POI、HTTP 429、5xx、超时、部分方向失败、无路线和无效 AK。
- 检查每种故障是否被正确分类、是否执行有限重试、是否触发熔断、页面是否明确显示状态、是否避免生成伪成功结果。
- 将线上实测、离线模拟和缓存结果分别标注，禁止混用。
- 生成一张简洁的工程证据表，并在技术设计文档或独立报告中说明复现命令。

### 验收标准

- 基准测试可通过单条命令运行，并输出机器可读结果。
- 至少给出一次逐点与批量策略的定量对比。
- 每种故障场景都有自动化断言和用户可见状态说明。
- 缓存命中耗时不得冒充冷启动性能。
- 性能结果包含样本次数，不能只报告一次最佳值。

### 证据产物

- 性能基线脚本与结果 JSON。
- 故障注入测试及测试报告。
- 工程优化对比表。
- CI 中对应的自动化检查入口。

## 5. 要求四：补充多源 POI 清洗与核验策略

### 目标

回应比赛交付要求中的“多源 POI 数据清洗策略”，同时避免为了形式强行引入不稳定或许可不清晰的实时数据源。

### 数据源分工

- 百度地图 Place Search：运行时主要候选数据源。
- 政府公开名录、机构官网、官方电话或公开页面：独立核验来源。
- 实地记录：高可信补充来源，用于核对名称、入口、类别和营业状态。
- 固定样例快照：仅用于无网络演示，不参与真实准确率计算。

### 开发任务

- 文档化每个数据源的用途、更新时间、许可边界、可信等级和可保存字段。
- 统一名称中的空格、全半角、分店后缀、行政区前缀和常见别名。
- 建立版本化类别词典，将多源类别映射为菜市场、药店、小学等项目标准类别。
- 优先按百度 UID 去重；跨来源记录按标准化名称、地址和空间距离联合匹配。
- 对同名不同址、同址多名、入口坐标偏移和不同来源营业状态冲突进行人工复核。
- 为每条合并记录保留来源列表、采集时间、原始类别、匹配方式和冲突状态。
- 明确第三方地图数据的使用与再分发边界，不将其错误地重新授权为项目开源数据。

### 验收标准

- 技术设计文档包含完整的数据源、清洗、去重、冲突处理和审计流程。
- 同一输入数据能够产生确定性清洗结果。
- 跨来源合并不会静默覆盖冲突信息。
- 真实核验报告能够追溯每条真值的独立来源。
- 数据与许可证说明不存在夸大或违规再分发。

### 证据产物

- 多源 POI 数据字典与类别映射表。
- 清洗与冲突处理流程说明。
- 典型去重、误分类和入口偏移案例。
- 与真实核验数据对应的来源审计字段。

## 6. 要求五：按评分标准重写三分钟演示

### 目标

让评委在三分钟内看到问题、核心功能、准确性证据和工程亮点，演示结构与评分表直接对应。

### 推荐时间轴

#### 0:00-0:25：问题与价值

说明固定半径无法反映道路绕行、河流、封闭小区和入口偏移，项目使用真实步行路网评估 15 分钟可达性。

#### 0:25-1:05：真实路网等时圈

输入或选择中心点，启动分析，展示 RouteMatrix 批量测时、等时圈边界、耗时分级和热力图。

#### 1:05-1:40：三类设施盲区

展示菜市场、药店和小学覆盖情况，打开服务灰区图层，点击灰区并解释缺失类别、面积、网格样本和证据。

#### 1:40-2:15：真实验证

展示独立核验样本量、查全率、分类准确率、边界误差和灰区准确率/召回率，并展示一个误差案例。

#### 2:15-2:42：工程优化与容错

展示逐点与批量计算对比，以及 429、超时或部分方向失败时的重试、限流、插值和明确状态提示。

#### 2:42-3:00：开源与收尾

展示 CI、Docker、离线演示和可审计报告，用一句话总结产品价值。

### 演示要求

- 主演示默认使用固定离线快照，避免现场网络和 AK 配额影响。
- 页面必须显式显示“样例快照”，不能将其描述成刚刚完成的在线分析。
- 使用真实社区报告证明在线能力和准确性。
- 演示前准备在线版、离线版、截图版和录屏版四级备用方案。
- 不在主演示中花费时间解释未完成的 P5，不承诺尚未实现的规划结论。
- 每个技术名词都必须回到用户价值，不做源码漫游式演示。

### 验收标准

- 连续排练至少 5 次，每次控制在 2 分 50 秒至 3 分钟内。
- 在断网、无 AK 环境下仍可完成主演示。
- 每个评分维度至少出现一项可见证据。
- 演示中所有数字均能在报告或测试产物中找到来源。
- 准备常见评委问题及不超过 30 秒的回答。

### 证据产物

- 更新后的 `docs/demo-script.md`。
- 三分钟演示录像。
- 现场演示检查表和备用方案。
- 评委问答清单。

将下面的提示词交给开发智能体时，应同时提供比赛 PDF、当前仓库和本文件。

请以比赛 PDF 的评分标准为唯一优先级依据：
1. 功能正确性与覆盖率 40%。
2. API 深度调用与工程优化 30%。
3. 产品交互与用户体验 15%。

本轮目标是完成参赛收口，不是无边界增加功能。请依次完成以下五项工作：

- 基准结果至少运行多次并记录环境，不得只报告最佳值。

- 以百度 Place Search 为运行时主源，以政府公开名录、机构官方页面/电话和实地记录为独立核验源，以固定快照为离线演示源。

- 保留现有架构和用户改动，采用小步提交式修改；每次修改都同步测试与文档。

- 不编造核验结果、准确率、基准结果、CI 状态或发布 URL。

5. 如果缺少真实人工数据、远程仓库权限或比赛平台信息，继续完成不依赖这些输入的模板、脚本和检查；不得自行伪造或发布。
